# Reuse Open Kernels, Build Knowledge-Guided CAD

The agentic-CAD landscape in late 2026 offers a clear split between reusable infrastructure and genuine research novelty. On the infrastructure side, mature open-source geometry kernels (build123d, CadQuery, OCCT) and production-ready MCP servers (build123d-mcp, neka-nat/freecad-mcp, MathWorks matlab-mcp-server) are permissively licensed and ready to reuse — the dominant architecture pattern across every runnable system is "LLM writes parametric Python → sandboxed execution → kernel geometry validation → VLM or compiler judge → repair loop" ([n3r/AgentCAD](https://github.com/n3r/AgentCAD), [CADSmith](https://github.com/jabarkle/CADSmith), [jdilla1277/agentcad](https://github.com/jdilla1277/agentcad), [armpro24-blip/cad-cae-copilot](https://github.com/armpro24-blip/cad-cae-copilot)). Commercial tools — MecAgent, Argus/Cosmon, Onshape AI, Autodesk Assistant — are enterprise-gated, stop at concept/parametric CAD plus drawings, and none is priced or designed for a single-person shop doing small-scale agricultural machinery ([mecagent.com](https://www.mecagent.com), [cosmon.com](https://www.cosmon.com), [getleo.ai](https://www.getleo.ai), [zoo.dev](https://zoo.dev)). The genuine novelty gap — and the defensible contribution for a research paper — is not another text-to-CAD generator but a **knowledge-guided, trust-tiered agentic loop that closes the loop from intent → validated parametric model → manufacturability and tolerance reasoning → shop deliverables**, evaluated on a domain corpus of small-scale agricultural machinery with frugality and manufacturability metrics that no current benchmark scores ([arXiv:2608.09296](https://arxiv.org/abs/2608.09296), [arXiv:2605.28579](https://arxiv.org/abs/2605.28579), [arXiv:2608.03062](https://arxiv.org/abs/2608.03062)). The practical recommendation is to reuse the open-source kernel + MCP + validator stack entirely, build only the knowledge layer (contracts, mechanism catalog, constraint graph, memory), and position the paper around domain-specific executable knowledge, process-aware DFM with tolerance stack-up, and closed-loop shop delivery.

## The open-source landscape splits into runnable systems and paper-only research

The code-available tier is dominated by build123d/CadQuery-based agent loops that all converge on the same architecture: the LLM emits parametric Python CAD code, the kernel executes it in a sandbox, geometric validity is checked against exact OCCT measurements, a VLM or compiler judge assesses design intent, and failures drive a repair loop. **n3r/AgentCAD** (Apache-2.0, 6 stars) treats "the model is code" and "the kernel is the referee" as first principles — every part is a small parametric Python script, every change is validated by real B-rep geometry (validity, volume, mass, bounding box, interference), and failures return as structured data (traceback, failing line, hints) for self-correction; it ships 109 MCP tools, a parts registry, and a nine-stage publish gate ([n3r/AgentCAD](https://github.com/n3r/AgentCAD)). **jabarkle/CADSmith** (no license specified, 37 stars) runs a five-agent pipeline (Planner → Coder → Executor → Validator → Refiner) with two nested correction loops and a dual verification approach combining exact OCCT kernel metrics with a VLM Judge; it uses a RAG knowledge base of 155 CadQuery API entries and reports a 38× reduction in mean Chamfer Distance vs. zero-shot on its own 100-prompt benchmark ([CADSmith](https://github.com/jabarkle/CADSmith), [arXiv:2603.26512](https://arxiv.org/abs/2603.26512)). **jdilla1277/agentcad** (Apache-2.0, 166 stars) provides a CLI + MCP server that runs a five-stage workflow (Inspect → Specify → Build → Validate → Deliver) and claims 48% higher CAD Score on the external CADGenBench benchmark (vendor-reported, not peer-reviewed) ([jdilla1277/agentcad](https://github.com/jdilla1277/agentcad)). **armpro24-blip/cad-cae-copilot** (MIT, 74 stars) is an AI-native CAD/CAE workbench whose MCP agent writes real build123d/OpenCASCADE geometry, runs deterministic critique, and continues into CalculiX FEA — the strongest verification story in the open-source tier, with credibility tiers stamped on every result ([armpro24-blip/cad-cae-copilot](https://github.com/armpro24-blip/cad-cae-copilot)). **Snitro/Pointer-CAD** (no license, 314 stars, CVPR 2026) uses an autoregressive pointer mechanism to select faces/edges on existing B-rep geometry, representing a different architecture from the code-generation paradigm ([Snitro/Pointer-CAD](https://github.com/Snitro/Pointer-CAD), [arXiv:2603.04337](https://arxiv.org/abs/2603.04337)). **Sunny-Hack/Seek-CAD** (MIT, 24 stars, ICLR 2026) runs a self-refinement loop with local DeepSeek inference over a ~40K-model dataset ([Sunny-Hack/Seek-CAD](https://github.com/Sunny-Hack/Seek-CAD)). **Cad-Kernel/MIRAGE-CAD** (0BSD, 0 stars) routes text, images, point clouds, and STEP through a shared construction representation, but its pipeline scripts carry hard-coded absolute paths (87 of 165 files) and are not turnkey ([Cad-Kernel/MIRAGE-CAD](https://github.com/Cad-Kernel/MIRAGE-CAD)).

The paper-only tier — **CAD-MLLM** ([arXiv:2411.04954](https://arxiv.org/abs/2411.04954)), **RA-CAD** ([arXiv:2608.05714](https://arxiv.org/abs/2608.05714)), **TOOLCAD** ([arXiv:2604.07960](https://arxiv.org/abs/2604.07960)), **TraceCAD** ([arXiv:2608.03062](https://arxiv.org/abs/2608.03062)), and **CADIR** ([arXiv:2608.00891](https://arxiv.org/abs/2608.00891)) — proposes concepts that have not yet been released as code but directly inform next-generation systems: critique-then-rewrite loops with learnable policies (RA-CAD), persistent repair state and skill memory (TraceCAD), cross-backend editable intermediate representations with Geometric Signature Matching (CADIR), and CAD-CoT with online curriculum reinforcement learning (TOOLCAD). The verification spectrum across all runnable projects spans three tiers: kernel geometry checks only (agentcad, MIRAGE-CAD), kernel + VLM judge (CADSmith), and compiler-as-judge replacing the VLM (CAD-Judge, [arXiv:2508.04002](https://arxiv.org/abs/2508.04002)) — the last explicitly arguing that VLM judges are slow and hackable. Several high-profile projects (CADSmith, Pointer-CAD) have no specified license on GitHub, creating legal uncertainty that favors the Apache-2.0 and MIT-licensed alternatives for reuse. **MCP is converging as the standard agent-to-CAD interface**: AgentCAD, agentcad, cad-cae-copilot, AnkusDrive, and CATIA-mcp all expose MCP servers, making it the de facto tool surface for the field.

## MCP servers and CAD tooling are production-ready and permissively licensed

The geometry kernel layer is settled: **build123d** (v0.13.0, Apache-2.0, Python 3.11–3.14) is a pure-Python parametric BREP framework on Open Cascade with a dual interface (stateless Algebra Mode and Builder Mode), while **CadQuery** (v2.8.0, Apache-2.0, 6.0k GitHub stars, Production/Stable) is the older, larger-community project with a fluent chain-based API; both share the same OCCT kernel underneath via **cadquery-ocp** (v8.0.1.1.0, Apache-2.0), so geometry quality is equivalent at the kernel level ([PyPI build123d](https://pypi.org/project/build123d/), [PyPI cadquery](https://pypi.org/project/cadquery/), [PyPI cadquery-ocp](https://pypi.org/project/cadquery-ocp/)). For LLM-generated code, build123d's algebraic mode is more composable and stateless, while CadQuery's larger community means more examples and third-party integrations.

On the MCP server side, **build123d-mcp** (pzfreo, Apache-2.0, 117 stars) is the most complete build123d server found — it executes code in a persistent session, renders PNG/SVG/DXF previews, measures volume/area/bounding boxes/topology, finds holes and bosses, checks printability and fit, exports STEP/STL/DXF/SVG, and produces 2D engineering drawing previews; its self-reported CADGenBench claim (raising the same model's score from 0.360 to 0.457 and validity from 88% to 100%) is not independently verified ([pzfreo/build123d-mcp](https://github.com/pzfreo/build123d-mcp)). The FreeCAD MCP ecosystem is fragmented — at least 9 distinct servers exist — with **neka-nat/freecad-mcp** (MIT, 2.9k stars) as the de facto leader, providing a two-component architecture (in-FreeCAD addon + external MCP server) with tools for model creation/editing, Python script execution, document inspection, and FEM analysis; most FreeCAD MCP servers require a running FreeCAD instance, unlike build123d-mcp which runs headless ([neka-nat/freecad-mcp](https://github.com/neka-nat/freecad-mcp)). **MathWorks' official matlab-mcp-server** (proprietary, 1.7k stars, Go binary) is production-ready but requires a MATLAB R2021a+ license and explicitly prohibits sharing the server across multiple users — each developer or agent needs their own license; it handles simulation/analysis workflows, not geometry creation ([matlab/matlab-mcp-server](https://github.com/matlab/matlab-mcp-server)).

For validation and rendering, **trimesh** (MIT, pure Python) is the natural choice for mesh-level validation (watertight, volume, inertia, boolean operations via Manifold3D); **ezdxf** (MIT, Production/Stable) is the standard for 2D DXF drawing export; **VTK** (BSD 3-clause, since 1994) and **Open3D** (MIT) are rendering backends. No dedicated "CAD validator MCP server" wraps these behind a single MCP interface, and no off-the-shelf MCP tool provides interference/clash detection or minimum clearance — these must be composed from OCP's `BRepAlgoAPI` boolean operations or FreeCAD's `Part.Shape.common()` and `Part.Shape.distToShape()` ([PyPI trimesh](https://pypi.org/project/trimesh/), [PyPI ezdxf](https://pypi.org/project/ezdxf/), [PyPI vtk](https://pypi.org/project/vtk/)). The licensing landscape is uniformly permissive across the reusable stack: Apache-2.0 (build123d, CadQuery, OCP), MIT (trimesh, ezdxf, freecad-mcp), and BSD 3-clause (VTK) all allow commercial use with attribution; only the MathWorks server imposes proprietary constraints.

## Commercial tools are enterprise-gated and stop at geometry plus documentation

Commercial agentic CAD splits into three camps: (1) **in-CAD copilots** that drive an existing CAD session (MecAgent, Argus/Cosmon, Adam, SOLIDWORKS Aura, Autodesk Assistant), (2) **standalone generative/computational CAD platforms** (nTop, Zoo/Zookeeper, Autodesk generative design), and (3) **engineering knowledge agents** that stop at retrieval, calculation, and part reuse rather than geometry (Leo AI, Onshape AI Advisor). **MecAgent** ($84–$417/mo per seat) operates as a desktop app connected to open SolidWorks/Inventor/CATIA/Fusion 360 sessions, generating parts, assemblies, and drawings from text or spec sheets; its verification posture is native CAD-kernel execution rather than a separate verifier, and its named customers include NASA, Apple, McLaren, and Ford ([mecagent.com](https://www.mecagent.com)). **Argus/Cosmon** (enterprise-negotiated) claims 52% average engineering speedup and 72% higher success rate (vendor-reported, unverified), spans CAD/CAE/PLM with Ansys Fluent integration, and offers cloud or on-premise deployment with BYOK and zero data retention ([cosmon.com](https://www.cosmon.com)). **nTop** explicitly positions itself not as an AI design tool but as "the geometry infrastructure that AI tools run on" — implicit models plug into Physics AI pipelines and its Lockheed Martin case study reports 400+ design variants simulated in 6–8 hours with a Fourier Neural Operator surrogate giving 1-second inference vs. 3600-second simulation (vendor-reported) ([ntop.com](https://www.ntop.com)). **Zoo/Zookeeper** offers an API-first, consumption-priced model (~$0.0083/second) with text-to-CAD described as open-source, but its roadmap stages are Design → Analyze → Manufacture with Analyze and Manufacture still "next" ([zoo.dev](https://zoo.dev)). **Leo AI** (enterprise, ~$15–$39/mo with contradictory secondary sources) provides CAD-aware knowledge retrieval over 120M+ vendor parts and calculations with citations to ASME/ISO clauses, but does not produce FEA or manufacturing output as its core ([getleo.ai](https://www.getleo.ai)).

The critical finding for a small-scale agricultural machinery designer is that **every commercial tool is either enterprise-priced/enterprise-positioned or a research/open-source project** — none is marketed for a frugal, single-person shop. The practical barriers are cost, data prerequisites (PLM/PDM/CAD data trails that a solo shop lacks), and the concentration of verification-heavy CAE in expensive enterprise platforms. The simulation/verification layer is the gap between "AI CAD" and "AI engineering": only nTop, aieng (open-source), and Argus (via Ansys integration) run real solvers, and most copilots stop at geometry plus drawings. Shop handoff (CAM, work instructions, drawings for production) is advertised by MecAgent and Autodesk but no vendor offers a fully autonomous design-to-manufacturing agent with verified output. **No commercial product was found that publicly documents an end-to-end pipeline from concept through verified FEA/CFD to CAM/shop-floor instructions in one agentic flow.**

## Benchmarks show far-from-solved geometry and leave domain knowledge unbenched

The named benchmarks instantiate a funnel model — sandbox/executability → geometric validity → engineering/design-intent checks — with increasing fidelity at each later stage. **CADEngBench** (arXiv:2608.09296) evaluates 300 parametric parts through B-rep validity, engineering/DFM checks, parameter-family perturbations, functional editing, and matched linear-static FEA in CalculiX, plus 150 body pairs through joint retrieval and kinematic verification; its headline finding is that editing supplied CAD is substantially easier than generating it, and complex edits and matched FEA remain difficult ([arXiv:2608.09296](https://arxiv.org/abs/2608.09296)). **RealCADBench** (arXiv:2609.03773) contains 12,632 tasks from 19 factory-automation categories with a 1,770-task evaluation slice; across six frontier-scale models, executability is 0.565–0.812, Solid IoU 0.2841–0.5379, and Surface IoU 0.112–0.217 — **no model leads all four metrics**, and the highest regime-balanced composite comes from a different model than the leaders on the component metrics ([arXiv:2609.03773](https://arxiv.org/abs/2609.03773)). **MUSE** (arXiv:2605.28579) pairs a three-stage protocol (code check → four binary OCCT geometry checks → rubric-based VLM judge scoring Functionality, Manufacturability, Assemblability) and shows a clear failure cascade from executable code to valid geometry to engineering-ready design ([arXiv:2605.28579](https://arxiv.org/abs/2605.28579)). **BenchCAD** (arXiv:2605.10865) provides 17,900 execution-verified CadQuery programs across 106 industrial part families and finds that systems often recover coarse outer geometry but fail to produce faithful parametric CAD programs, with common failures including replacing sweeps, lofts, and twist-extrudes with simpler sketch-and-extrude patterns ([arXiv:2605.10865](https://arxiv.org/abs/2605.10865)). **CADSmith's** self-reported results on its own 100-prompt benchmark (100% execution up from 95%, Chamfer 28.37 → 0.74) carry weak external validity due to the small, self-defined benchmark ([arXiv:2603.26512](https://arxiv.org/abs/2603.26512)). The CUAWright paper (arXiv:2610.04116) reports that harness/tooling alone yields 8.1%–41.6% relative improvements on CADGenBench and BenchCAD, meaning any framework must report harness-controlled comparisons, not raw scores ([arXiv:2610.04116](https://arxiv.org/abs/2610.04116)).

The metric landscape is dominated by executability/validity as the universal first gate, followed by solid/surface IoU and Chamfer distance, with F-score, Hausdorff distance, and VLM-judge scores as secondary; constraint satisfaction and design-intent alignment are the newest differentiator, and edit success / iteration count / token cost / latency are emerging as agent-specific metrics. Two findings are decisive for positioning: **IoU and Chamfer reward "looks like" over "works as"** — RealCADBench shows no model leads all four metrics, and MIRAGE-CAD reports that executable validity, geometric fidelity, and parametric responsiveness diverge substantially ([arXiv:2608.28669](https://arxiv.org/abs/2608.28669)); and **rubric/VLM judges are becoming the differentiator but are also a reliability risk** — MUSE validates its VLM judge with human annotation, while CAD-Judge warns that VLM-based review "can be expensive and may introduce reward hacking" ([arXiv:2508.04002](https://arxiv.org/abs/2508.04002)).

The unbenched gaps are stark. **Tolerance stack-up and CAD-agent assembly benchmarks returned zero arXiv hits** — suggestive, not conclusive, evidence of a gap. No benchmark scores a generated CAD model on tolerance stack-up, GD&T callout correctness, BOM completeness, or a drawing set. Manufacturability is generic (MUSE's rubric), not process- or region-specific. Simulation gates are nascent — only CADEngBench touches engineering behavior via CalculiX FEA, and domain-specific loads (soil reaction on tools, PTO/linkage kinematics, fatigue of cyclic soil loads) appear unbenchmarked. Frugality/cost is unreported as a design-quality metric in any benchmark surveyed. The closed loop to the shop is unbuilt as an evaluated artifact — Design-to-Plan (arXiv:2608.24039) turns CAD + drawings into process plans but is a separate downstream task, not a generation-time gate ([arXiv:2608.24039](https://arxiv.org/abs/2608.24039)). No agriculture-specific CAD corpus or benchmark exists; the only LLM-agriculture-machinery paper found (CIAMM, arXiv:2407.20588) addresses machinery management/consultation, not CAD design ([arXiv:2407.20588](https://arxiv.org/abs/2407.20588)).

## Recommendation: reuse the stack, build the knowledge layer, claim domain novelty

The reuse-vs-build decision is clear: **reuse everything at the kernel, MCP server, and validator level; build only the knowledge and domain-specific layers.** The implementation stack should be: **build123d as the primary CAD kernel** (algebraic mode for LLM-generated code, Apache-2.0, dual-mode API) with **build123d-mcp as the execution/validation server** (subprocess isolation, rendering, measurement, export); **FreeCAD via neka-nat/freecad-mcp as the verification and CAE bridge** (interference, clearance, mass properties, TechDraw drawings); **MATLAB via the official matlab-mcp-server for simulation gates** (torque, stability, traction, tolerance propagation); **trimesh + ezdxf as mesh validation and 2D drawing libraries** wrapped behind custom MCP tools; and **ThinkToCad's own contracts + knowledge graph + memory layer** as the differentiator. The knowledge layer is where the build investment goes: an executable, constraint-grounded knowledge base (mechanism catalog, DFM rules, local stock sizes, fit/standard tables) that is unit-consistent and retrieved as structured data rather than prose RAG; process-aware DFM checks (welding, sheet metal, machining, manual) plus a tolerance-stack reasoner; closed-loop delivery to GD&T-annotated 2D drawings, BOM, and process plan; and a domain-specific benchmark with frugality metrics (cost per part, material utilization, agent token/cost per accepted design).

Five defensible novelty claims emerge from the landscape analysis. **First, domain knowledge as a first-class executable artifact** — positioning the contribution as a knowledge-guided agent whose retrieved constraints are executable and unit-consistent, distinct from CADSmith's API-doc RAG and ArtisanCAD's expert-skill distillation, and directly targeting the gap that no agriculture-machinery corpus exists ([arXiv:2603.26512](https://arxiv.org/abs/2603.26512), [arXiv:2607.05750](https://arxiv.org/abs/2607.05750)). **Second, manufacturability plus tolerance stack-up as scored gates** — process-aware DFM checks plus a tolerance-stack reasoner scored numerically, addressing the two zero-result gaps (tolerance stack; CAD-agent assembly) and going beyond MUSE's generic rubric ([arXiv API query: tolerance stack](http://export.arxiv.org/api/query?search_query=all:%22tolerance+stack%22+AND+all:CAD+AND+all:LLM), [arXiv:2609.05559](https://arxiv.org/abs/2609.05559)). **Third, closed-loop delivery to shop artifacts** — evaluating end-to-end deliverables (GD&T-annotated 2D drawings, BOM, process plan) generated from the model, not just the solid; Design-to-Plan shows the downstream reasoning exists but no benchmark requires it as part of generation ([arXiv:2608.24039](https://arxiv.org/abs/2608.24039)). **Fourth, a frugality/cost metric and a domain benchmark** — reporting cost per part/implement, material utilization, and agent token/cost alongside validity and IoU; no benchmark surveyed reports design cost or frugality ([jdilla1277/agentcad](https://github.com/jdilla1277/agentcad), [arXiv:2608.03062](https://arxiv.org/abs/2608.03062)). **Fifth, simulation gates for agricultural loads** — domain-specific kinematics (hitches, PTO, linkages) and load cases (soil reaction, cyclic fatigue) as verification gates, extending CADEngBench's generic FEA/kinematic tracks to agronomic machinery ([arXiv:2608.09296](https://arxiv.org/abs/2608.09296)).

Two positioning cautions are warranted. Because harness choice alone moves CADGenBench/BenchCAD scores by 8–42%, any headline must be a matched, harness-controlled comparison ([arXiv:2610.04116](https://arxiv.org/abs/2610.04116)). And because benchmark scores reverse across test sets (the textcad-bench repo shows model rankings flipping across T1/T2/T3), the domain benchmark should report per-tier and per-regime results rather than a single number ([github.com/prashantkul366/textcad-bench](https://github.com/prashantkul366/textcad-bench)). The field has moved from single-shot text-to-CAD generation (2023–2024) to stateful, tool-mediated, iterative agents (2025–2026), and the next defensible step is not a better generator but a knowledge-guided loop that closes the gap between "valid solid" and "manufacturable, assemblable, inspectable product" — precisely the gap that no current benchmark, commercial tool, or open-source project addresses for small-scale agricultural machinery.
