# Build your own Python agent framework

Building your own Python agent framework is less about inventing a new loop and more about assembling a small set of well-understood primitives—a model client, a tool registry, a context manager, and an async ReAct loop—and then hardening them with protocols, observability, evaluation, safety, and cost controls. Every major framework surveyed (OpenAI Agents SDK, Anthropic's Claude Agent SDK, Google ADK, LangGraph, AutoGen/AG2, CrewAI, Pydantic AI, smolagents, LlamaIndex Workflows) reduces to the same shape: assemble model input from state, call the LLM, execute tool calls (in parallel where independent), append results, and repeat until a final output, a handoff, an interrupt, or `max_turns`. The consensus across OpenAI, Anthropic, and Google is to start with a single agent maximized for capability and to introduce multi-agent orchestration only for high-value, parallelizable, breadth-first work, since multi-agent runs burn roughly 15× the tokens of a chat. Production readiness is not a feature you add at the end; it is a set of cross-cutting layers—MCP for tools, A2A for agent delegation, OpenTelemetry tracing, eval harnesses, guardrails, checkpointing, and prompt caching—that must be designed into the loop from the first commit.

## Every framework reduces to one ReAct-shaped loop with five exit conditions

An agent, per OpenAI's practical guide, is an LLM-driven system that independently accomplishes tasks on a user's behalf, distinct from LLM-augmented apps where the LLM does not control workflow execution; it is built from three components—Model, Tools, Instructions—and its core characteristics are that the LLM manages workflow decisions, recognizes completion, self-corrects, and can halt and hand back to the user, while tools are dynamically selected within guardrails ([OpenAI practical guide](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)). Anthropic's "Building effective agents" (Dec 2024) makes the same distinction in different words: workflows orchestrate LLMs and tools through predefined code paths, while agents let the LLM dynamically direct its own processes and tool usage, and it recommends finding the simplest solution possible and only increasing complexity when needed, since agentic systems trade latency and cost for performance ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). The canonical loop itself is ReAct-shaped: assemble model input from state → call the LLM → if there are no tool calls, return a final output; otherwise execute the tool calls (in parallel where independent) → append tool results to history → repeat, bounded by `max_turns` or a termination condition. OpenAI's `Runner.run()` loops until a final-output tool is invoked or the model returns text with no tool calls; LangChain's `create_agent`, Pydantic AI's `CallToolsNode` loop, the OpenAI Agents SDK, and smolagents all share this shape, with frameworks exposing primitives (graph nodes, steps, events, handoffs) onto which patterns are layered rather than hard-coding one loop ([running_agents doc](https://openai.github.io/openai-agents-python/running_agents/); [opensource survey](https://docs.langchain.com/oss/python/langgraph/overview)).

The five termination conditions to implement are: (1) no tool calls / final output (text or structured); (2) `max_turns` exceeded (OpenAI raises `MaxTurnsExceeded`, with `max_turns=None` disabling the cap); (3) a handoff transferring control to another agent; (4) a HITL interrupt or pause (LangGraph's `interrupt()` pauses and saves state via a checkpointer); and (5) a guardrail tripwire or an explicit exit signal such as smolagents' `final_answer` tool call, ADK's `exit_loop` setting `escalate=True`, LlamaIndex's `StopEvent`, or AutoGen's `MaxMessageTermination` ([running_agents doc](https://openai.github.io/openai-agents-python/running_agents/); [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts); [smolagents guided tour](https://huggingface.co/docs/smolagents/guided_tour)). The practical starting skeleton is an implicit async loop with `before_model`/`before_tools`/`after_turn` hook points, because ADK, Pydantic AI, and the OpenAI SDK all treat async as primary with sync wrappers, and because an implicit loop is simplest to debug while remaining migratable to a graph or event-driven state machine later without rewriting tool or model code. LangGraph models the same loop as a directed `StateGraph` over a typed state object executed by a Pregel runtime with checkpointing and HITL via `interrupt()`; Pydantic AI wraps a pydantic-graph state machine whose `agent.iter()` yields `UserPromptNode`, `ModelRequestNode`, `CallToolsNode`, `End`; ADK's `Runner` orchestrates agent/tool/callback events and commits via services; AutoGen is conversation-centric with teams defining turn-taking; CrewAI runs tasks under `Process.sequential` or `Process.hierarchical`; and LlamaIndex Workflows are event-driven with `@step` methods whose type annotations define edges. The trade-off is real: an implicit async loop is easiest to debug but hard to make durable or resumable; a graph is flexible and checkpointable but carries boilerplate and API churn (LangGraph's v1→v2 streaming migration shows this); an event-driven state machine is composable and resumable but complex. Start implicit, add hooks, migrate only when durability demands it.

The model layer should be a provider-agnostic client with `chat(messages, tools, response_format) → ModelResponse`, `stream(...) → AsyncIterator[StreamEvent]`, and `count_tokens(...) → int`, with usage and cost tracked on every response. OpenAI recommends the Responses API for new agent projects—stateful-by-default, typed Items, an agentic loop within a single request, built-in tools, preserved reasoning state, and 40–80% cache improvement—while Chat Completions remains the portable lowest common denominator; Anthropic's `tool_use` blocks yield `stop_reason: "tool_use"` and `strict: true` guarantees schema conformance; ADK takes a required model string id such as `"gemini-flash-latest"` with `thinking_config`. The key design implication is to model the internal turn as a sequence of typed "items" (message, function_call, function_call_output, reasoning) rather than flat messages, so both client-managed and server-managed state work, and to implement against Chat Completions semantics with Responses-specific optimizations (reasoning state, built-in tools) as optional capabilities. Retries, rate limits, and token counting are cross-cutting concerns that most frameworks leave to user configuration—only CrewAI ships a built-in `max_rpm`—so build exponential backoff with jitter on 429/5xx, per-provider token buckets, and circuit breakers yourself.

Structured output has two forms: (a) `response_format`/`json_schema` mode where the model returns JSON matching a schema, and (b) a tool-based form where a `submit_result` tool's arguments are the schema. Validate with Pydantic and, on `ValidationError`, return the error to the model for retry ("reflection and self-correction," per Pydantic AI). OpenAI `strict: true` requires all fields in `required` and `additionalProperties: false`; Anthropic `strict: true` guarantees conformance; ADK's `output_schema` only reliably supports tools on Gemini 3.0+, otherwise falling back to a `set_model_response` tool. A portable warning: strict structured outputs on every turn can suppress tool calls on non-OpenAI backends such as vLLM, so portable frameworks may need two-stage orchestration—gather with tools, then finalize structured.

## Tools are the product; MCP is their transport

Tools are Python functions whose signatures and docstrings become JSON schemas, and the framework validates arguments, executes (async, in parallel where safe), and returns structured results; errors are returned to the model as tool results for retry rather than raised. OpenAI's function calling emits `function_call` items with `call_id`; the app executes and returns `function_call_output` linked by `call_id`; `parallel_tool_calls` is true by default; `max_tool_calls` caps built-in tool calls per response. Anthropic's tool use has Claude decide when to call based on request and tool description, returning `tool_use` blocks. OpenAI classifies tools as Data (retrieve context), Action (mutate external systems), and Orchestration (agents as tools), and stresses that similarity and overlap matter more than raw count—more than 15 distinct tools can work, while fewer than 10 overlapping tools can fail. The cross-provider schema contract is an object with `name`, `description`, and `parameters` (JSON Schema: `type: "object"`, `properties`, `required`); OpenAI strict mode requires all params in `required` and `additionalProperties: false`; Anthropic uses `input_schema`; MCP's `tools/list` returns `name`/`description`/`inputSchema`.

The design that follows: a `@tool` decorator that introspects the signature into a Pydantic model, a `ToolRegistry` with `schemas()` and `execute()`/`execute_all()`, and a `ToolResult` dataclass carrying `call_id`, `content`, `is_error`, and `metadata`. Validate args with Pydantic; on `ValidationError` or any exception, return `ToolResult(is_error=True, content=str(exc))` so the model can retry. Never raise into the loop. Run read-only or `concurrency_safe` tools via `asyncio.gather`; run stateful tools sequentially in call order to avoid corruption. Wrap tools with input/output validators that can reject or replace content, and make tripwires raise terminal exceptions for catastrophic violations (OpenAI's tool-guardrail pattern). Two design rules from the literature dominate reliability: Anthropic's agent-computer interface guidance—choose formats the model writes easily (close to natural internet text, no formatting overhead), give tokens to think, poka-yoke arguments, and require absolute filepaths, which fixed SWE-bench errors—and OpenAI's instruction that descriptions should state when to invoke and how to build arguments, with developer instructions disambiguating similar tools and preferred ordering. Tool design is positioned as equal-or-greater effort than prompt design, and Anthropic's tool-writing post recommends generating dozens of realistic multi-step tasks, running simple agentic while-loops, collecting metrics (runtime, tool calls, tokens, errors), analyzing transcripts, and holding out test sets to avoid overfitting description tweaks.

MCP is the standard transport: an open standard (JSON-RPC 2.0) for connecting AI apps to external systems, promoted by Anthropic as "USB-C for AI," with a host creating one client per server; servers expose tools, resources, and prompts; transports are stdio (local) and Streamable HTTP (remote, OAuth recommended). Tools are discovered via `tools/list` and executed via `tools/call`; the protocol is stateless with protocol version and capabilities in `_meta`. A production framework should keep three planes separate: (a) an MCP client for consuming tools/resources/prompts from any MCP server plus an MCP server for exposing its own tools; (b) A2A for delegating to remote agents and receiving delegated tasks; (c) an OpenAI-compatible HTTP API (`/v1/chat/completions` and optionally `/v1/responses`) so existing clients, SDKs, and routers work unchanged. MCP's optional `EventStore` and session id give a ready-made resumability hook for long-running tool calls.

## Context engineering, not prompt engineering, decides long-horizon reliability

Context is finite with diminishing returns: transformer attention is n² pairwise, and longer contexts reduce recall (context rot). Anthropic frames context engineering as the successor to prompt engineering because agents run long loops where context, not a single prompt, determines behavior. The practical model: represent history as typed messages/items; budget tokens per request; on overflow, compact (summarize) older turns or clear stale tool results; keep a per-run scratchpad; use just-in-time retrieval for long-term memory; place prompt-cache breakpoints on stable prefixes. System prompts should sit at the "right altitude" between brittle hardcoded logic and vague guidance, organized into sections (Identity, Instructions, Examples, Context); few-shot examples should be diverse and canonical, not laundry lists; tools must be token-efficient and self-contained; and agents keep lightweight identifiers (paths, queries, links) and load data at runtime via tools (progressive disclosure). Claude Code uses `CLAUDE.md` up front plus glob/grep just-in-time.

The three long-horizon techniques are compaction (summarize nearing-limit history and restart with the summary; Claude Code keeps the 5 most recently accessed files), structured note-taking/agentic memory (`NOTES.md`/TODOs), and sub-agent architectures (isolated context windows returning 1k–2k token summaries). Run compaction when estimated tokens exceed ~80% of budget: keep system + tools (cached) + last K turns verbatim; summarize the middle into a single summary message; clear raw tool results beyond a window, retaining only their summaries. Long-term memory should expose `add(text, metadata)` and `search(query, k) → list[Memory]`, with implementations from in-memory keyword to SQLite+FTS to a vector store, retrieving top-k only when relevant (just-in-time), not always. Persist state two ways: checkpointers (thread-scoped graph state snapshots, short-term) and stores (cross-thread key-value, long-term)—LangGraph's `InMemorySaver`/`SqliteSaver`/`PostgresSaver`; ADK's `Session` with `InMemorySessionService`/`VertexAiSessionService`/`DatabaseSessionService` and `MemoryService` with `InMemoryMemoryService`/`VertexAiMemoryBankService`/`VertexAiRagMemoryService`; the OpenAI Agents SDK's `SQLiteSession`/Redis/Mongo/Dapr/encrypted variants plus server-managed `conversation_id`/`previous_response_id`; CrewAI's short/long/entity memory plus LanceDB-backed `remember`/`recall`/`extract_memories` and `@persist` (SQLite) with resume/fork. The scratchpad-versus-messages rule: keep intermediate values (plans, retrieved doc IDs, tool outputs) in a per-run state dict and inject a compact summary into messages, not the full data.

Prompt construction follows cache order: stable prefixes first, volatile content last. Anthropic's cache prefix order is tools → system → messages, with default 5-min TTL (refreshed free on use), optional 1-hour at 2× base, writes at 1.25×/2×, reads at 0.1×, and a lookback window of 20 blocks per breakpoint; place `cache_control` on the last block whose prefix is identical across requests. OpenAI caches automatically with a 1,024-token minimum; Google requires explicit breakpoints. The design rules: never put volatile content (timestamps, user-specific data) in the cached prefix; version and test tool descriptions with held-out tasks; use templating (`{var}`, as ADK does) for dynamic state injection rather than string concatenation; and include persistence/tool-calling/planning reminders for models that need them (GPT-4.1 family). Over-specified prompts can hurt with stronger models—"smarter models need less prescriptive engineering" (Anthropic)—so calibrate to the model.

## Multi-agent orchestration costs 15× the tokens and earns it only for breadth-first work

Multi-agent systems excel for breadth-first queries pursuing multiple independent directions: Anthropic's orchestrator-worker (Claude Opus 4 lead + Claude Sonnet 4 subagents) outperformed single-agent Opus 4 by 90.2% on an internal research eval but burns ~15× the tokens of a chat, and token usage explains 80% of BrowseComp performance variance. The architecture: a lead agent analyzes the query, saves its plan to Memory (because context beyond 200k tokens gets truncated), creates specialized subagents that search with interleaved thinking, synthesizes, optionally iterates, then hands off to a CitationAgent; subagent outputs go to the filesystem to minimize the "telephone" game. Prompting principles: delegate with objective/output format/tools/boundaries; scale effort to query complexity (simple: 1 agent, 3–10 calls; complex: more than 10 subagents); tool design is critical; let agents improve themselves (a tool-testing agent rewrote descriptions and ran 40% faster); start wide then narrow; guide thinking; parallel tool calling cuts research time up to 90%.

The patterns to implement: prompt chaining, routing, parallelization (sectioning/voting), orchestrator-workers, and evaluator-optimizer (Anthropic's five workflow patterns); manager (agents as tools, central control) versus decentralized (handoffs, peers transfer control) (OpenAI); and deterministic workflow agents—`SequentialAgent`, `ParallelAgent`, `LoopAgent` (ADK)—plus `Swarm` speaker selection by most recent `HandoffMessage` (AutoGen), `Process.sequential`/`Process.hierarchical` (CrewAI), and `managed_agents` (smolagents). Handoffs are best implemented as ordinary tool calls (`transfer_to_<agent>`), as both AutoGen Swarm and the OpenAI Agents SDK do, so any tool-calling model can drive routing without a separate orchestrator. OpenAI's `handoff()` supports `tool_name_override`, `input_type`, `input_filter`, `is_enabled`, `nest_handoff_history` (which compacts transcripts into summary segments); agents-as-tools via `as_tool()` keeps a manager in control.

The central design choice is shared state versus message passing: shared state (ADK session state, LangGraph state dict) is fast and enables templating but couples agents and complicates concurrency; message passing (AutoGen thread, A2A tasks) is decoupled and auditable but adds serialization. Recommendation: use a shared scratchpad for in-process subagents (summaries only, 1–2k tokens) and message passing (A2A) for cross-service agents; write large subagent outputs to the filesystem and pass paths, not content. Avoid infinite loops with `max_turns`/`max_iterations`, termination conditions, `exit_loop` escalation, final-answer tools, HITL breakpoints, and state-based convergence checks (no new information in N turns). The consensus recommendation from OpenAI and Anthropic is single-agent-first: maximize a single agent's capability before splitting, and split only when complex if-then-else logic or tool overload (similarity/overlap, not raw count) demands it.

## Production hardening is a layered stack, not a feature list

Interoperability: implement three planes—MCP client/server for tools, A2A server/client for agent delegation, and an OpenAI-compatible HTTP front door. A2A is Google's open protocol for peer-to-peer agent communication over HTTP: agents discover each other via Agent Cards at `/.well-known/agent.json`; tasks carry a lifecycle (`submitted`, `working`, `input-required`, `completed`, `canceled`, `failed`, `rejected`, `auth-required`, `unknown`); RPC methods include `message/send`, `message/stream` (SSE), `tasks/get`, `tasks/cancel`, `tasks/pushNotificationConfig/*`, `tasks/resubscribe`; content units are `TextPart`/`DataPart`/`FilePart`; auth is OAuth2/OIDC at the HTTP layer. A2A complements MCP: MCP gives agents tools and data (vertical), A2A gives agents to agents (horizontal). AgentCard `skills` map to registered capabilities, and `contextId`/`taskId` map to thread/run identifiers, so an A2A adapter is a thin shim over the internal run model.

Observability: trace every run as an OpenTelemetry trace tree—a top-level `invoke_agent` span with child `chat`/inference spans per LLM call and `execute_tool` spans per tool invocation—carrying `gen_ai.*` attributes (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`, `gen_ai.conversation.id`, `gen_ai.tool.name`, cache token counts). Content capture (prompts, completions, tool args/results) is opt-in because it may contain sensitive data; default captures only metadata. The conventions are still "Development" status, so pin to a specific semconv version and make attribute names configurable. Record tool calls as first-class spans to enable trajectory evaluation and failure attribution; compute cost from token usage × price table in the tracer itself so spend caps can be enforced inline. Minimum record: run/trace id, agent name/version, conversation id, model + provider, per-call token usage (input/output/reasoning/cache read-write), latency, finish reason, tool name + args + result + duration, errors, and opt-in redacted content.

Evaluation: evaluate at three levels—final task success, trajectory (tool selection/order/efficiency), and stepwise LLM-as-judge. Deterministic task-success metrics where possible (τ-bench compares final DB state; environment-state hash matching); LLM-as-judge (preferably agent-as-judge with trajectory access, which outperformed output-only judges on code tasks at parity with humans, though at high cost) for nuanced quality; run offline in CI as regression tests and online in production with sampling. A practical harness scores four metrics: task success, tool-call accuracy (precision/recall/F1 over the multiset versus a reference trace), step efficiency (optimal/actual steps), and cost per task. Persist structured trajectories, intermediate states, and artifacts so custom metrics can be added without re-running the agent. Outcome-only judges are structurally blind to agents that reach the right answer the wrong way, so pair discrimination against clean parent trajectories and split reporting by outcome survival.

Guardrails and safety: OWASP ranks Prompt Injection (LLM01) #1 for the second consecutive year; defenses are probabilistic—researchers consistently find bypasses within weeks, and Cisco argues prompt injection cannot be parameterized like SQL—so treat it as a property to manage, not a bug to fix. Layer guardrails: validate and sanitize inputs and outputs; defend against direct and indirect prompt injection by keeping untrusted content (tool results, retrieved docs) in separate message roles/sections with provenance, never concatenated into the system prompt; enforce tool allow/deny lists and least privilege; redact PII on both inputs (before logging) and outputs (before returning); require human approval for high-risk actions; sandbox tool execution. Apply standard web security to agent endpoints (TLS, auth at the HTTP layer, least privilege), scope tool permissions per agent/run, defend against SSRF (block private IPs and metadata endpoints) and path traversal (canonicalize paths), inject secrets via a secret resolver at tool runtime (never in prompts, traces, or AgentCards), and enforce per-tenant and per-tool rate limits with backpressure surfaced as retryable errors. Per-run budget object: max tokens, max tool calls, max wall-clock time, max spend USD, enforced in the loop and the tracer.

Reliability: design the loop as a durable, resumable workflow—persist checkpoints per step, make side effects idempotent with idempotency keys, retry transient failures with backoff and timeouts, support HITL interrupts as first-class state (like A2A's `input-required`/`auth-required`) with a durable pending-approval record and a resume entrypoint, and use a task queue to decouple request handling from execution. LangGraph's durable execution requires a checkpointer and thread id, with durability modes `exit` (persist only on exit/interrupt, best performance, no mid-run recovery), `async` (small crash risk), and `sync` (persist before next step, highest durability); non-deterministic or side-effecting ops must be wrapped in tasks/nodes. Separate "pure" agent steps (deterministic, no I/O) from "effect" steps (LLM calls, tool calls, I/O) so only effects are retried and replay stays deterministic. For long-running agents, prefer an external durable executor (Temporal/Cadence) or a task queue plus checkpoint store rather than in-process only. Exactly-once tool execution is not achievable in general; idempotency keys are the documented mitigation.

Cost and latency: (1) enable provider prompt caching with stable prefixes (41–80% savings across providers; OpenAI/Google cache automatically, Anthropic requires explicit breakpoints; the Anthropic optimizing guide notes turn on caching plus trim unneeded tokens as free levers, and that a 25-token status line at the front of a system prompt made a small agent cost more than caching off); (2) route simple sub-tasks to cheaper models (Haiku/Sonnet vs Opus, 5–15× cheaper), configurable by token count/complexity with per-task overrides, quality-gated on the eval suite; (3) trim or compress context with awareness of cache invalidation—trimming is deterministic with zero added latency but weak long-range recall and invalidates the prompt cache (a case study showed median 12% token reduction, median $0.32 cache-miss penalty, break-even at median 38 turns); compression retains memory compactly but adds latency/cost and risks context poisoning; (4) parallelize independent tool calls; (5) pre-warm caches. Manus AI cites KV-cache hit rate as the single most important production metric. Combine caching + trimming + routing + parallel tool calls; track cost-per-task and KV-cache hit rate as first-class metrics in the tracer.

## Conclusion

The blueprint that emerges is deliberately unglamorous: a single async ReAct loop with typed items, a Pydantic-validated tool registry, a token-budgeted context manager with compaction, and a stable cached prompt prefix, wrapped in MCP/A2A/OpenAI-compatible protocol adapters, OpenTelemetry tracing, an eval harness with trajectory capture, layered guardrails, checkpointed durable execution, and cache-aware cost controls. Earn every layer of complexity with measurement rather than speculation: start with one agent and one tool, add a second agent only when tool confusion or instruction non-compliance is measured, add compression only when trimming's recall loss shows up in evals, and add multi-agent only for breadth-first work that justifies 15× the tokens. The frameworks surveyed agree on this incrementalism; the production failures they document come from teams that skipped the measurement step.
